# BudStacks template builder

A BudStacks template is the look of one brand's shop: its home page and About page. It is **data, not code**: four files and an `assets/` folder that tell the platform which sections to render, with what content, in what style.

```
{slug}/
  layout.json            which nav, sections and footer, and each one's content and options
  defaults.json          the design system (colours, fonts, radius, shadows…) and page content
  styles.css             a few lines of scoped CSS, often none
  template.config.json   name, slug and marketplace description
  assets/                every image, logo and video the template shows
```

You compose from a fixed library. You never write a component, and you never emit a key the platform does not read.

## The contract

`references/contract/` is generated by the platform from the code that renders templates. It is the only authority on what exists.

| File | Use it for |
|---|---|
| `contract/component-catalog.md` | Every section, what it is, every config key with its type, default and options |
| `contract/section-schemas.json` | The same, for the validator |
| `contract/design-system.schema.json` | What `designSystem` may contain |
| `contract/registry.json` | Section types by category; nav and footer types |

If a key is not in the catalogue, the runtime ignores it and the validator rejects it. Do not carry keys over from older templates or from memory: `animation`, `dividerTop`, `gradients`, `primary-scale`, radius and spacing scales and named shadows are all dead.

Refresh the contract when the platform changes: `scripts/sync-contract.sh <path-to-budstack-saas>`.

## Workflow

### Phase 1 — Get the design

Work out which input you have. All three end in the same thing: a filled-in handoff specification (the block at the end of `references/design-brief.md`).

**A. Design handoff.** A designer or a design tool was given `references/design-brief.md` and has returned the specification, usually with desktop and mobile pictures. Read the specification first; the pictures show intent.
- Check every section type against `contract/registry.json` and every option against the catalogue.
- Where the handoff asks for something the library cannot do, choose the closest section and record it as a gap. Do not approximate it with CSS.
- Where the handoff is silent (a density, a variant, an eyebrow), decide it yourself using `references/quality-rubric.md` and say what you decided.

**B. Brand interview.** No design exists. Ask, in one message: brand name and what it stands for; audience and market (country matters for the disclaimer); tone (clinical, wellness, lifestyle, luxury, street); colours or an existing logo; fonts if any; which images they can supply. Then draft the handoff specification yourself and get it approved before generating files.

**C. Figma URL.** Follow `references/figma-import.md`, which ends in the same specification.

If the person wants a design made first, give them `references/design-brief.md` to pass to their designer or design tool, and stop until the handoff comes back.

### Phase 2 — Decide the design system and the page

Present these decisions and get agreement before writing files. Use `references/quality-rubric.md` as the checklist.

**Design tokens** (one value each; this is the whole of `designSystem`):

| Key | Choices |
|---|---|
| `schemaVersion` | `2` — always |
| `colors.primary` `secondary` `accent` `background` `text` `heading` | required; raw HSL channels, e.g. `"178 48% 21%"` — never hex, never `hsl()` |
| `colors.surface` `border` `success` `warning` `error` `info` | optional; surface and border are derived when unset |
| `typography.fontFamily.body` `heading` | required; a CSS font stack or a catalogue font id |
| `typography.fontFamily.accent` | optional |
| `typography.fontSize.base` `hero` `section` | px as strings; defaults `"16"` `"60"` `"40"`. `hero` and `section` are the desktop sizes; the platform scales them down on phones |
| `typography.fontWeight.body` `heading` | `300 400 500 700` and `400 500 600 700 800`, as strings |
| `typography.letterSpacing` | `tight normal wide wider` (body) |
| `typography.heading.letterSpacing` `transform` `lineHeight` | `tight normal wide`; `none uppercase`; `tight snug normal` |
| `borderRadius.container` `button` | `none small medium large`; `rounded square pill` |
| `shadows.card` `tint` | `none soft medium bold`; `neutral brand` |
| `spacing.scale` | `compact normal comfortable` |
| `button.size` | `small medium large` |
| `glassEffect` `buttonHoverEffect` | `none light heavy`; `none lift glow scale pulse` |
| `animationType` `dividerStyle` | `none fade-up slide-right zoom-in`; `none wave slant curve` |

Colour guidance is in `references/color-theory.md`; font pairing in `references/typography.md`.

**The page:**

1. One navigation type and one footer type (`contract/registry.json`). Every footer carries the Dr Green partner mark; choose `partnerMark: "full"` or `"compact"`. It cannot be removed, and FooterSimple is always compact.
2. One hero, first. Then 4 to 8 sections that build trust, show the offer and end in a call to action. `references/layout-archetypes.md` has starting patterns; choose by brand fit.
3. For each section decide: `eyebrow` (aim for at least half the headed sections), `density` (`compact`, `normal`, `spacious` — use at least two across the page), `variant` and `iconStyle` where the section has them, and `textAlign`.
4. Decide which sections get their own colours (a dark band, a tinted block). That is a `colorOverrides` object on the section, never CSS.

### Phase 3 — Write the files

**layout.json**

```json
{
  "version": "1.0.0",
  "navigation": "NavMinimal",
  "navigationConfig": {
    "links": [{ "label": "About", "href": "/about" }],
    "cta": { "label": "Check eligibility", "href": "/consultation" }
  },
  "sections": [
    {
      "id": "hero",
      "type": "HeroSplit",
      "config": { "eyebrow": "Clinic", "title": "…", "subtitle": "…", "ctaText": "Check eligibility", "imageUrl": "assets/hero.jpg" }
    },
    {
      "id": "values",
      "type": "ValueProps",
      "config": { "eyebrow": "Why us", "heading": "…", "variant": "bordered", "density": "spacious", "items": [] },
      "colorOverrides": { "background": "210 50% 12%", "text": "0 0% 96%", "heading": "0 0% 100%" }
    }
  ],
  "footer": "FooterBrand",
  "footerConfig": { "partnerMark": "compact", "tagline": "…", "disclaimer": "…" },
  "settings": {
    "wrapperClass": "template-{slug}",
    "googleFontsUrl": "https://fonts.googleapis.com/css2?family=…&display=swap"
  }
}
```

- Every section needs a unique `id` and a `type` from the registry. `config` holds only keys the catalogue lists for that type.
- Links are relative (`/about`, `/products`, `/consultation`, `/the-wire`, `/contact`, `/faq`); the platform adds the store prefix.
- Images are `assets/<file>` and the file must exist. Never leave an image or logo field as an empty string: remove the item or supply the file.
- Leave out a `subtitle` the design does not have. In a v2 store a section shows no subtitle of its own. Headings, items and button labels are different: a section still falls back to built-in text for those, so always set them.
- HeroSplitImages shows `subtitle` as a small pill badge above the title; the paragraph under the title is `description`.
- `settings.wrapperClass` is exactly `template-{slug}`. `settings.googleFontsUrl` must load every font family the design system names, unless you use catalogue font ids and set no URL at all.
- `settings.sectionPadding` (`"3rem"` or `"3rem/4rem/5rem"`) replaces the base padding for the whole page. Leave it out unless the design needs it; density does the per-section work.
- There are no per-section animation or divider keys. Motion and dividers are the two store-wide tokens.

**defaults.json**

```json
{
  "template": "{slug}",
  "slug": "{slug}",
  "logoPath": "assets/logo.png",
  "heroImagePath": "assets/hero.jpg",
  "designSystem": {
    "schemaVersion": 2,
    "colors": {
      "primary": "210 78% 22%", "secondary": "205 55% 48%", "accent": "196 75% 30%",
      "background": "210 25% 98%", "text": "210 20% 28%", "heading": "210 50% 12%"
    },
    "typography": {
      "fontFamily": { "body": "'Plus Jakarta Sans', system-ui, sans-serif", "heading": "'Fraunces', Georgia, serif" },
      "fontSize": { "base": "16", "hero": "64", "section": "40" },
      "fontWeight": { "body": "400", "heading": "600" },
      "heading": { "letterSpacing": "tight", "transform": "none", "lineHeight": "tight" }
    },
    "borderRadius": { "container": "large", "button": "pill" },
    "shadows": { "card": "soft", "tint": "brand" },
    "spacing": { "scale": "normal" },
    "button": { "size": "medium" },
    "glassEffect": "none",
    "buttonHoverEffect": "lift",
    "animationType": "fade-up",
    "dividerStyle": "none"
  },
  "pageContent": {},
  "navigation": {},
  "footer": {}
}
```

`designSystem` contains the keys in the Phase 2 table and nothing else. `pageContent` holds the About page and other fixed-page content: see `references/page-content.md`. Copy rules are in `references/copy-style-cannabis.md`.

**styles.css**

Most v2 templates need little or none. The platform already styles headings (fluid sizes, tracking, case), buttons, cards, framed images, shadows, section spacing, eyebrows and focus rings from the design system.

What CSS is still for: a gradient or image background on one section, a decorative accent, a custom keyframe. Rules:

- At most 120 lines. No `!important`, `@import`, `@tailwind`, `@apply` or `theme()`.
- Every selector starts with `.template-{slug}`.
- Hooks that exist: `[data-section-type="HeroSplit"]`, `[data-section-id="values"]`, `#values`, and roles inside a section — `[data-ui~="section"]`, `[data-ui~="header"]`, `[data-ui~="heading"]`, `[data-ui~="subtitle"]`, `[data-ui~="eyebrow"]`, `[data-ui~="card"]`, `[data-ui~="media"]`, `[data-ui~="hero"]` (HeroSplit), `[data-ui~="button"]` (with `[data-variant="primary|accent|secondary|ghost|inverse|custom"]`).
- Never target a Tailwind utility class (`.rounded-2xl`, `.bg-white`, `[class*="shadow"]`): they are internal and change.
- Never declare `--tenant-color-*`: colours come from `designSystem.colors`, and the platform strips these lines. For a tint use alpha: `hsl(var(--tenant-color-primary) / 0.08)`.
- Wrap any animation in `@media (prefers-reduced-motion: no-preference)`.

If you find yourself fighting the platform with CSS, the thing you want is a design token or a `colorOverrides`.

**template.config.json**

```json
{
  "id": "{slug}",
  "slug": "{slug}",
  "name": "Display Name",
  "description": "One line on the look and who it is for",
  "category": "medical|wellness|modern|luxury|street|editorial",
  "tags": ["…"],
  "features": ["…"],
  "author": "BudStacks Platform",
  "version": "1.0.0"
}
```

The slug is lowercase letters, digits and hyphens, and is the same in all four files.

### Phase 4 — Assets

Put every image, logo and video in `assets/` at production size (`references/assets-pipeline.md`, sizes also in `design-brief.md` §5). One photographic treatment across the template. Logos are transparent PNG or SVG. If the handoff describes an image but supplies none, say so and ask for it; do not ship a template with a missing or placeholder image.

**When the handoff describes its images but supplies none.** Say so before anything else, with the list of images, sizes and a prompt for each. Then either the owner supplies the files, or you generate them with `scripts/generate-image.mjs` (it needs a Higgsfield API key ID and secret in the environment; the script's header says how). Write one shared style paragraph and put it in front of every prompt, so the set looks like one shoot. Look at every result: redo any with a face, readable text, a brand, or the wrong subject. **Never publish or hand over a template whose images are stand-ins**, and never use another brand's product photographs.

### Phase 5 — Validate

```bash
node scripts/validate-template.mjs ./{slug}
```

Node 20 or later, no install. It must report **zero errors**. An error is something the runtime would ignore or render badly: an unknown section or key, a value off its list, a design-system key the runtime does not read, a missing asset or font, unreadable text, an unfilled `{{PLACEHOLDER}}`, or CSS that breaks the rules above. Fix the template, not the validator.

Warnings are rubric items. For each one, either fix it or write down why it stands.

### Phase 6 — Upload and review

1. Upload: the platform takes a template from a **public GitHub repository** and nothing else (there is no zip upload). Put the four files and `assets/` at the root of the repository, on `main`. Then BudStacks super admin → Templates → Upload: give the repository URL and a template name. **The name you type becomes the slug** (lowercased, spaces to hyphens), so type one that gives the slug in the files: "V2 Pilot" for `v2-pilot`. A v2 template that fails the platform's own schema check is rejected at upload with the same messages the validator gives.
2. The preview is at `/store/preview/{slug}`.
3. Get screenshots at 375, 768 and 1440px without running a browser locally: in the `budstack-saas` repository, run the **Template preview screenshots** workflow with the slug (`gh workflow run template-preview-screenshots.yml -f slug={slug}`), then download the artifact.
4. Review the three screenshots against `references/quality-rubric.md`. Fix and re-upload until every row passes.
5. Report: the validator result, what you checked on each screenshot, and any gaps between the design and what the library could do.

## Rules that are not negotiable

- **Data only.** Four files and assets. No `.tsx`, no scripts, no extra pages.
- **Contract only.** Every section type, config key and design token comes from `references/contract/`.
- **Version 2.** `designSystem.schemaVersion` is `2`.
- **The Dr Green partner mark stays.** Full or compact; never hidden by config or CSS.
- **Compliance.** No medical claims; adult patients only; a disclaimer for the brand's market in `footerConfig.disclaimer` (`references/copy-style-cannabis.md`).
- **Accessibility.** Text contrast 4.5:1 or better, including inside colour overrides; meaningful `alt` text on content images (`references/accessibility-checklist.md`).
- **No placeholders.** Real copy, real images, no empty fields.
- **Validator passes before upload.**
